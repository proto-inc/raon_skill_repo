# raon-spec-to-docs

프로젝트 아이디어를 **사용자와 질문을 주고받으며** 확정 사양으로 만들고, 번호가 붙은 `docs/` 폴더에 단계별 문서로 정리한다. 앱(iOS·Android·Flutter)과 웹(사이트·웹 서비스) 모두에 쓴다.

이 스킬은 특정 AI 도구에 묶이지 않는다. Claude Code, Codex, Cursor 등 `SKILL.md`를 읽는 도구에서 쓴다. 아래 '도구별 기능 대응'에서 지금 쓰는 도구에 있는 기능을 고르고, 없으면 대체 방법을 쓴다.

## 도구별 기능 대응

| 필요한 기능 | Claude Code | Codex | Cursor | 기능이 없을 때 |
|---|---|---|---|---|
| 질문지 (선택지 질문) | `AskUserQuestion` | `request_user_input` | `AskQuestion` | [텍스트 질문지](#텍스트-질문지-형식) |
| 병렬 조사 | 서브에이전트 (`Agent`) | 서브에이전트 기능이 있으면 사용 | 서브에이전트 기능이 있으면 사용 | 주제별로 차례대로 조사 |
| 웹 조사 | `WebSearch`·`WebFetch` | 웹 검색 도구 | 웹 검색 도구 | 사용자에게 공식 자료 링크를 요청하고 미검증으로 표시 |
| 미리보기 확인 | 셸에서 헤드리스 브라우저 | 셸에서 헤드리스 브라우저 | 셸 또는 내장 브라우저 | 사용자에게 열어 보고 확인해 달라고 요청 |

- 도구 이름은 버전에 따라 바뀔 수 있다. 지금 세션에서 실제로 쓸 수 있는 도구를 먼저 확인한다.
- 질문지 도구가 있어도 꺼져 있거나 실패하면 **텍스트 질문지로 바로 바꾼다.** 질문을 생략하고 혼자 정하지 않는다.

## 핵심 원칙

1. **문서 순서대로 하나씩.** 한 단계 문서를 끝내면 "✅ N번째 문서 완료"를 알리고, 다음 단계에서 무엇을 정할지 소개한 뒤 넘어간다. 사용자가 "다음"이라고 하기 전에는 다음 단계로 가지 않는다.
2. **결정은 질문지로 받는다.** 사양을 구체화하는 질문은 가능한 한 선택지가 있는 질문지로 묻는다. ([질문지 규칙](#질문지-규칙))
3. **기존 자료는 참고만 한다.** 이전 문서·코드가 있으면 사실 확인용으로만 읽고, 문장을 그대로 옮기지 않는다.
4. **모든 결정을 기록한다.** 결정은 각 단계 `README.md`의 결정 표에 ID(F-, D-, DS- …)를 붙여 남긴다. 질문하지 않고 정한 값은 "기본값 (검토 필요)"로 따로 표시한다.
5. **미정은 미정으로 둔다.** 비용 한도·라이선스·법적 판단처럼 사용자가 정하지 않은 것은 임의로 확정하지 않고 '결정 대기'에 남긴다.
6. **사실은 조사하고 출처를 단다.** 가격·약관·플랫폼 제약은 웹 조사로 확인하고, 확인하지 못한 내용은 "(미검증)"으로 표시한다.
7. **사용자 수준에 맞춰 설명한다.** 사용자가 잘 모르는 분야(도메인 용어, 플랫폼 네이티브 기능 등)는 질문 안에서 설명하고, 사용자가 익숙한 기술에 비유한다.

## 질문지 규칙

- 한 번에 **최대 3문항**(도구 공통 최소 한도), 문항마다 **선택지 2~4개**를 준다. 도구가 더 많이 허용해도 3문항을 넘기지 않는다.
- **추천 선택지를 첫 번째**에 두고 라벨 끝에 `(추천)`을 붙인다. 도구가 영어 표기를 요구하면 `(Recommended)`를 쓴다.
- 문항마다 짧은 머리말(2~3단어)을 붙인다. 예: `등록 방법`, `보관 기간`
- 선택지 외 답('기타')을 항상 받을 수 있게 한다.
- 선택지마다 설명에 장단점·비용·난이도·영향을 한두 문장으로 쓴다.
- 질문 본문에 필요한 배경 설명(용어, 제약)을 넣는다. 긴 배경은 질문지 앞에 짧은 표나 목록으로 먼저 보여 준다.
- 여러 개를 고를 수 있는 질문(알림 종류, 언어 등)은 복수 선택으로 묻는다. 도구가 복수 선택을 지원하지 않으면 '해당하는 것을 모두 고르세요'라고 쓴다.
- 위치·배치처럼 말로 헷갈리는 선택은 선택지 미리보기(도구가 지원하면) 또는 질문 앞에 텍스트 그림으로 보여 준다.
- **자유 서술이 더 맞는 질문만 텍스트로** 묻는다. 예: 첫 컨셉 설명, 기능 나열.
- 한 단계의 질문은 2~3회 질문지로 나눠 묻는다. 큰 방향을 먼저 정하고, 답에 따라 생긴 세부 질문을 그다음에 묻는다.

### 텍스트 질문지 형식

질문지 도구가 없거나 동작하지 않으면 아래 형식으로 묻고, 사용자가 `1-A, 2-B, 3-기타: …`처럼 답하게 한다.

```
**Q1. 등록 방법** — 항공편을 어떻게 등록할까요?
  A. 편명+날짜 입력 (추천) — 예매 직후 바로 등록, 구현이 가장 쉬움
  B. 탑승권 스캔 — 체크인 후에만 가능
  C. 기타: 직접 적어 주세요

**Q2. 알림 종류** (여러 개 선택 가능) — …
  A. … B. … C. …

👉 답 예시: `1-A, 2-A·B`  /  모르겠으면 "추천대로"
```

**답변 처리**
- '기타(Other)'로 들어온 자유 답변은 그대로 따르되, 모호하면 선택지로 다시 확인한다.
- 답이 위험을 만들면 한 번 더 확인한다. 위험의 예: 심사 반려, 기능 범위 축소, 비용 초과, 법적 문제. **결과를 구체적인 예로 보여 주고** 확인한다.
- 사용자가 디자인·문서의 **특정 부분 수정**을 요청하면 기존 컨셉을 유지한 채 그 부분만 바꾼다. 제약 때문에 컨셉을 바꿔야 하면 먼저 묻는다.
- 사용자가 확정한 결과물(아이콘·핵심 디자인 등)은 기본값으로 기억하고, 이후에는 **더하기만** 제안한다.

## 시작하기

1. **프로젝트 유형**을 확인한다: 모바일 앱 / 웹사이트(정보·마케팅) / 웹 서비스(로그인·데이터) / 앱+웹.
2. **기존 자료**를 확인한다: 기존 docs, 코드, git 저장소 여부. 기존 자료는 참고만 한다고 알린다.
3. **폴더 구조를 제안**한다. ([docs 폴더 구조](#docs-폴더-구조))
4. **컨셉을 자유 서술로 묻는다.** 아래를 아는 만큼 답해 달라고 하고, 모르는 것은 "모르겠다"로 둬도 된다고 알린다.
   - 한 줄 소개
   - 만들게 된 계기, 해결하려는 불편
   - 대상 사용자
   - 사용 시점 / 방문 상황
   - 생각한 기능 전부
   - 이름의 의미
   - 하지 않을 것

## docs 폴더 구조

```

├── 01-planning/
│   └── product-requirements.md   기획서 (왜·누구를·무엇을)
├── 02-research/

    ├── README.md              결정 RL-xx, 결정 대기
    ├── store-listing.md       (앱) 스토어 등록 정보 / (웹) 도메인·SEO·메타 정보
```

- **필요한 파일만** 만든다. 예: 외부 데이터 갱신이 없으면 `data-sync.md`를 만들지 않는다.
- 각 단계 `README.md` 맨 위에는 머리 표를 둔다.

  ```
  | 항목 | 내용 |
  |---|---|
  | 문서 상태 | 초안 v1 (검토 중) → 확정 v1 (날짜) |
  | 작성일 | YYYY-MM-DD |
  | 이전 문서 | [링크] |
  | 다음 문서 | [링크] |
  ```

- **결정 ID 접두어**

  | 접두어 | 용도 |
  |---|---|
  | F- | 기능 |
  | D- | 조사 결정 |
  | DS- | 화면 설계 |
  | VD- | 시각 디자인 |
  | TD- | 기술 |
  | IM- | 구현 |
  | TS- | 테스트 |
  | RL- | 출시 |
  | S- | 화면 |
  | T- | 테스트 시나리오 |
  | M- | 마일스톤 |
  | R- | 조사 문서 |

- 문서끼리는 상대 경로 링크로 잇고, 작성 후 링크가 깨지지 않았는지 확인한다.

## 단계별 절차

각 단계는 **질문 → 문서 작성 → 완료 보고**로 진행한다.

### 01. 기획 (`01-planning/product-requirements.md`)

컨셉 답변을 정리해 보여 준 뒤 질문지로 구체화한다.

| 앱 질문 예 | 웹 질문 예 |
|---|---|
| 핵심 입력·등록 방식 | 사이트 목적 (홍보·판매·예약·커뮤니티) |
| 보여 줄 정보 범위 | 핵심 페이지·전환 목표 (문의·구매·가입) |
| 알림 종류·시점 | 회원 기능 필요 여부 |
| 지원 지역·언어 | 지원 언어·지역 |
| 로그인 필요 여부·방식 | 콘텐츠 관리 주체 (개발자 / 운영자 CMS) |
| 플랫폼 특화 기능 (위젯 등) 첫 출시 포함 여부 | 결제·외부 연동 |

**문서 구성**
- 한 줄 소개
- 해결할 문제
- 대상 사용자
- 사용 흐름 (시점별 표)
- 첫 출시 기능 F-xx
- 지원 범위
- 하지 않을 것
- 다음 버전 후보
- 제약 조건 (비용·플랫폼·공개 여부)
- 결정 대기
- 용어 정리

### 02. 조사 (`02-research/`)

1. 기획서에서 **불확실한 것**을 뽑는다. 예: 외부 데이터·API의 가격과 약관, 플랫폼 제약, 스토어 심사·법적 요건, 운영비, 경쟁 서비스.
2. 독립된 주제는 **병렬로** 조사한다. 서브에이전트가 없으면 주제별로 차례대로 조사한다. 조사 지시에는 아래를 넣는다.
   - 출처 URL
   - "(미검증)" 표시 요구
   - 가입하거나 실제 키를 쓰지 말 것
   - 분량 제한
3. 조사하는 동안 사용자에게 주제별 조사 내용과 그 이유를 표로 보여 준다. 예상되는 충돌(예: 예산 vs 범위)도 미리 알린다.
4. 결과를 주제별 R-n 문서로 쓰고, `README.md`에 결정·위험·결정 대기를 모은다.
5. 결과 때문에 기획을 바꿔야 하면 질문지로 결정받고, **기획서에 반영해 버전을 올린다.**

### 03. 화면 설계 (`03-design/`)

1. 기능(F-xx)과 연결한 **화면(페이지) 목록 초안**을 보여 준다.
2. 질문지로 정한다.

   | 앱 | 웹 |
   |---|---|
   | 홈 구성 | 사이트맵·상단 메뉴 |
   | 탭·내비게이션 구조 | 랜딩 구성 |
   | 시각·숫자 표시 기준 | 반응형 기준 (모바일 우선 여부) |
   | 앱 밖 표시(알림·위젯) 시점 | |
   | 언어 선택 방식 | 언어 선택 방식 |
   | 산출물 형태 | 산출물 형태 |

3. 화면별 **텍스트 스케치**와 **상태별 화면**을 쓴다. 상태 예: 빈 목록, 로딩, 오류, 오프라인, 권한 없음.
4. 여러 화면에 공통인 규칙은 `display-rules.md`로 뺀다.
5. **시각 디자인**은 질문지로 방향을 정한다.
   - 분위기·메인 색
   - 다크 모드 지원 여부
   - 기본 컴포넌트 vs 커스텀
   - 숫자·제목 글꼴
   - 카드 스타일
   - 아이콘·로고 컨셉
   - 결과물 형태 (문서 / HTML 미리보기 / Figma)
6. HTML 미리보기를 만들면 아래 순서로 검증한다.
   - 헤드리스 브라우저로 스크린샷을 찍어 **직접 확인한 뒤** 사용자에게 연다. 이미지를 볼 수 없는 도구라면 사용자에게 확인을 요청한다.
     ```
     # macOS 예
     "/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" --headless=new --screenshot=out.png --window-size=W,H file:///…/index.html
     # Linux/Windows 예: chrome 또는 chromium 에 같은 옵션
     ```
   - 글자와 배경의 **명도 대비를 계산**해(WCAG AA 4.5:1) 문서에 표로 남긴다.
   - 아이콘·로고는 실제 표시 크기(예: 60pt, 32px)로도 렌더링해 확인한다.
   - 비슷한 경쟁 아이콘이 있는지 조사해 위험을 알린다.

### 04. 기술 설계 (`04-technical/`)

질문지로 정한다.
- 기존 코드 처리 (새로 작성 / 재사용)
- 상태 관리·구조
- 데이터 쓰기 경로 (클라이언트 직접 / 서버 경유)
- 서버·호스팅 지역 (변경 불가 여부 강조)
- 서버 언어
- 외부 데이터 갱신 주기
- 데이터 보관 기간

웹이면 다음도 정한다.
- 렌더링 방식 (SSG / SSR / SPA)
- 호스팅
- CMS
- 분석 도구와 쿠키 동의

**문서 구성**
- `architecture.md`: 구성도, 계층, 폴더 구조, 빌드 구성
- `data-model.md`: 컬렉션·테이블, 필드, 삭제 규칙
- `api-spec.md`: 공통 규칙, 에러 코드, 사용자별 한도, 함수·엔드포인트별 입력·출력
- `security.md`: 위협과 대응 표, 권한 규칙, 비밀 정보 보관 위치, 개인정보 수집·보관 표
- `README.md`의 '구현 전 검증 항목': 키 발급 후에야 알 수 있는 것을 모아 둔다.

### 05. 구현 계획 (`05-implementation/`)

1. **git 저장소 여부를 확인한다.** 저장소가 아니면 삭제는 되돌릴 수 없다고 알리고, 정리 방법을 질문지로 정한다. (git 시작 후 정리 / legacy 폴더 / 새 저장소)
2. 질문지로 정한다.
   - 코드 작성 주체 (Claude 작성 + 설명 / 일부 직접 / 직접 + 리뷰)
   - 이미 준비된 계정·서비스 (복수 선택)
   - 목표 시점
3. 마일스톤을 정한다.
   - M0 준비
   - M1 불확실한 기술 검증 (시제품)
   - 이후 핵심 기능
   - ★ 핵심 기능 완성 지점
   - 부가 기능
   - 출시 준비
4. 각 마일스톤에 **작업, 담당(사용자/Claude), 완료 기준**을 쓴다.
5. 사용자가 콘솔에서 직접 해야 하는 일은 `setup-checklist.md`에 위치까지 적는다. 실제 키는 채팅에 쓰지 말라고 안내한다.

### 06. 테스트 계획 (`06-testing/`)

1. 질문지로 정한다.
   - CI 범위
   - 베타 테스트 여부
   - 실기기·브라우저 종류
2. 테스트 대상을 나눈다.
   - **반드시 자동 테스트**: 틀리면 사용자 피해·보안 문제가 생기는 곳. 예: 계산, 권한, 입력 검증, 외부 호출 한도.
   - **수동 확인**: 그 밖의 부분.
3. 시나리오 T-xx를 영역별로 묶고, **마일스톤별로 통과해야 할 시나리오**를 표로 연결한다.
4. 테스트 데이터는 가상 데이터만 쓰는 규칙을 적는다.

### 07. 출시 준비 (`07-release/`)

1. 질문지로 정한다.
   - 출시 국가 (앱) / 도메인 (웹)
   - 정책 문서 호스팅 위치
   - 문의 창구 (회사 메일 사용 지양)
   - 이름·부제
2. 문서를 쓴다.
   - 등록 정보: 스토어 또는 SEO 메타
   - 개인정보 처리방침·약관 내용, 스토어 개인정보 라벨 또는 쿠키 고지
   - 출시 체크리스트
   - 예상 반려·장애와 대응
   - 출시 후 운영 주기
3. 법적 판단은 "법률 자문 아님 · 확인 필요"로 표시한다.

### 08. 확정과 이관

1. 사용자가 확정하면 모든 단계 문서를 `확정 v1 (날짜)`로 바꾸고, `docs/README.md` 상태 표를 갱신한다. "(검토 필요)" 기본값은 확정 표시로 바꾼다.
2. 새 저장소로 옮기기로 했다면 아래 순서로 진행한다.
   1. `git init`
   2. 새 문서만 복사
   3. 작업 규칙(`AGENTS.md`/`CLAUDE.md`), `README.md`, `SECURITY.md`, `.gitignore` 작성
   4. 비밀 키·이메일 패턴 검사
   5. 커밋
3. **공개 원격 저장소 생성·푸시는 반드시 질문지로 확인**받은 뒤 한다.
4. 작업 규칙 파일 이름은 쓰는 도구에 맞춘다. Codex·Cursor는 `AGENTS.md`, Claude Code는 `CLAUDE.md`를 읽는다. 여러 도구를 쓰면 `AGENTS.md`를 원본으로 두고, `CLAUDE.md`에서는 그 파일을 참조한다.

## 지켜야 할 것

- 실제 API 키·토큰·비밀번호·개인 여행/주문 정보는 문서·채팅·커밋에 쓰지 않는다. 사용자에게 붙여 넣어 달라고 하지 않는다.
- 미구현 기능을 문서에 완료로 쓰지 않는다.
- 조사 결과와 다른 주장, 확인하지 않은 가격·제약을 사실처럼 쓰지 않는다.
- 사용자에게 보이는 문장은 짧고 쉽게 쓴다. 표와 목록을 활용한다.
